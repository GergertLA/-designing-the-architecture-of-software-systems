### Компоненты внутри контейнера «Парсер новостей»

Модуль загрузки новостей - самполучает новости от внешних источников:
- через RSS,
- через API,
- через webhooks,
- из потоковых источников.

Модуль извлечения текста - берёт HTML страницы и извлекает:

- заголовок,
- текст новости,
- возможно — картинки.
Удаляет лишние элементы вроде меню, баннеров, рекламных блоков.

Модуль метаданных - определяет ключевые данные новости:

- источник,
- время публикации,
- автора,
- URL,
- язык.

Модуль удаления дублей - проверяет, была ли такая новость уже загружена, помогает избежать повторной обработки одного и того же материала.

Модуль сохранения - сохраняет оригинальный текст в файловом хранилище и записывает основные данные в базу данных.

Модуль оповещения о новой статье - сообщает другим частям системы (нормализатору), что появилась новая новость, которую нужно обработать дальше.

Модуль обработки ошибок - следит за ошибками:
- делает повторные попытки при временных сбоях;
- отправляет сообщения об ошибках в мониторинг;
- записывает проблемные события для анализа.

### Пояснение сущностей

**NewsSource**
Хранит информацию о новостных источниках (сайты, каналы, API), из которых система получает новости. Используется для управления списком источников и группировки данных.

**NewsArticle**
Описывает отдельную новостную статью. Содержит основные данные о публикации и ссылку на файл с полным текстом статьи, сохранённый во внешнем хранилище.

**SentimentResult**
Хранит результат анализа тональности конкретной новости. Показывает, является ли новость позитивной, негативной или нейтральной, а также уверенность модели в результате.

**PricePrediction**
Содержит результат прогноза влияния новости на цену Bitcoin. Используется для оценки возможного направления движения цены и вероятности такого сценария.

**AggregatedMetrics**
Хранит агрегированные показатели по новостям за определённый период и источник. Используется для построения графиков и сводной аналитики на дашборде.

### Пояснение связей

NewsSource — NewsArticle (1 : 0..*)
Один новостной источник может публиковать множество новостей, каждая новость относится к одному источнику.

NewsArticle — SentimentResult (1 : 0..1)
Для каждой новости может быть рассчитан один результат анализа тональности либо он может отсутствовать, если анализ ещё не выполнен.

NewsArticle — PricePrediction (1 : 0..1)
Новость может использоваться для построения прогноза влияния на цену, но прогноз не является обязательным.

NewsSource — AggregatedMetrics (1 : 0..*)
Для одного источника может храниться несколько агрегированных показателей за разные даты или периоды.

AggregatedMetrics — SentimentResult (1 : 0..*)
Агрегированные метрики рассчитываются на основе множества результатов анализа тональности отдельных новостей.

## Применение основных принципов разработки

Серверная часть реализована на Python и отвечает за загрузку новостей, их первичную обработку и сохранение результатов в базу данных и файловое хранилище. Клиентская часть представлена дашбордом Grafana, который напрямую читает данные из базы данных и не содержит собственной бизнес-логики. Такой подход минимизирует сложность системы и чётко разделяет ответственность компонентов.

### Серверная часть (Backend)

#### Принцип KISS (Keep It Simple, Stupid)

**Идея:** простая логика, минимум условий и абстракций.

**Что сделано:**
- нет сложной микросервисной архитектуры;
- одна БД;
- Grafana работает напрямую с БД;
- сервер выполняет только приём и сохранение данных.

```python
# Пример: загрузка новостей из источника
def fetch_news(feed_url: str) -> list[dict]:
    response = requests.get(feed_url, timeout=10)
    response.raise_for_status()
    return parse_rss(response.text)
```

Функция выполняет одну очевидную задачу — получить новости по URL и вернуть результат парсинга. Здесь нет сложных цепочек вызовов, скрытой логики или универсальных «комбайнов». Такой код легко читать, тестировать и сопровождать, что напрямую соответствует принципу KISS.

#### Принцип YAGNI (You Aren’t Gonna Need It)

**Идея:** не реализовывать функциональность «на будущее».

**Что НЕ сделано намеренно:**
- нет пользовательской авторизации;
- нет сложных ролей;
- нет API для чтения данных (Grafana не нуждается);
- нет отдельных сервисов агрегации.

```python
# Пример: минимальная модель результата тональности
@dataclass
class SentimentResult:
    article_id: UUID
    sentiment: str
    confidence: float
```

В модели отсутствуют дополнительные поля (например, история изменений, версия модели, список токенов), так как они не требуются для текущей задачи. Реализованы только те данные, которые реально используются для анализа и визуализации. Это снижает объём кода и сложность системы, что отражает принцип YAGNI.

#### Принцип DRY (Don’t Repeat Yourself)

**Идея:** не дублировать логику и структуры данных.

**Что сделано:**

- единые модели данных (SentimentResult, PricePrediction);
- агрегация хранится в отдельной таблице, а не считается каждый раз.

```python
# Пример: единый метод сохранения статьи
def save_article(article: NewsArticle, db: Session) -> None:
    db.add(article)
    db.commit()

# Использование
article = NewsArticle(
    id=uuid4(),
    title=title,
    published_at=published_at,
    source_id=source_id,
    storage_key=storage_key
)

save_article(article, db)
```

Логика сохранения статьи в БД вынесена в одну функцию и используется во всех местах системы. Это исключает дублирование SQL-кода и снижает риск расхождений при изменениях. Такой подход полностью соответствует принципу DRY.

#### Принципы SOLID
**S — Single Responsibility Principle**

**Идея:** один класс — одна ответственность.

- парсер — только получает и сохраняет новости;
- модели — только анализируют;
- Grafana — только отображает данные.

```python
class NewsFetcher:
    def fetch(self, source_url: str) -> list[dict]:
        ...

class ArticlePersister:
    def save(self, article: NewsArticle) -> None:
        ...
```

NewsFetcher отвечает только за загрузку данных, а ArticlePersister — только за сохранение. Изменение логики загрузки не затрагивает код сохранения и наоборот.

**O — Open/Closed Principle**

- Можно добавить новую модель анализа, не меняя структуру БД и дашборд.
```python
class BaseFetcher:
    def fetch(self, source: str):
        raise NotImplementedError

class RSSFetcher(BaseFetcher):
    def fetch(self, source: str):
        return parse_rss(source)
```

Для добавления нового типа источника (например, API) не требуется менять существующий код — достаточно создать новый класс. Это демонстрирует расширяемость без модификации.

**L — Liskov Substitution Principle**

- любая модель анализа может заменить другую, если она отдаёт результат в том же формате.

**I — Interface Segregation Principle**

- нет «толстых» интерфейсов;
- каждый модуль использует только нужные ему данные.

**D — Dependency Inversion Principle**
```python
class ParserService:
    def __init__(self, fetcher: BaseFetcher):
        self.fetcher = fetcher
```

Сервис зависит не от конкретной реализации загрузчика, а от абстракции. Это упрощает тестирование и замену компонентов.

### Клиентская часть (Frontend)
Клиентская часть — Grafana, без отдельного веб-приложения. Данные визуализируются через SQL-запросы, алерты настраиваются в Grafana.

```sql
-- Пример SQL-запроса в панели Grafana
SELECT
  date,
  avg_sentiment,
  positive_count,
  negative_count
FROM aggregated_metrics
WHERE source_id = $__uuid
ORDER BY date;
```

Grafana не содержит бизнес-логики и использует уже подготовленные агрегированные данные. Это соответствует KISS и YAGNI: клиентская часть максимально простая и не дублирует серверные вычисления (DRY).


## Дополнительные принципы разработки
### BDUF (Big Design Up Front — масштабное проектирование прежде всего)

**Суть принципа.** BDUF предполагает детальное проектирование всей системы до начала разработки. Заранее описываются архитектура, компоненты, взаимодействия, модели данных и возможные сценарии расширения.

**Применимость к проекту.**
В рамках данной работы принцип BDUF применяется ограниченно. С одной стороны, на раннем этапе были спроектированы базовая архитектура системы, схема данных и основные потоки обработки информации (парсинг → анализ → хранение → визуализация). Это позволило избежать архитектурных ошибок и обеспечить согласованность компонентов.


С другой стороны, полный BDUF с детальной проработкой всех будущих функций (например, пользовательских ролей, расширенных моделей прогнозирования или дополнительных источников данных) был бы избыточным. Проект носит исследовательский характер, а требования могут уточняться в процессе работы. Поэтому выбран компромиссный подход - проработана только необходимая на данный момент архитектурная основа.

### SoC (Separation of Concerns — принцип разделения ответственности)

**Суть принципа.** SoC заключается в том, что каждая часть системы отвечает за строго определённый набор задач и не смешивает разные виды ответственности.

**Применимость к проекту.** Данный принцип полностью применим и активно используется. Архитектура системы построена таким образом, что:

- парсер отвечает только за загрузку и сохранение новостей;
- модули анализа выполняют исключительно обработку текста и прогнозирование;
- база данных хранит результаты анализа и агрегаты;
- Grafana отвечает только за визуализацию и алерты, не содержащие бизнес-логики.

Такое разделение упрощает сопровождение системы, облегчает отладку и делает архитектуру более наглядной и устойчивой к изменениям.

### MVP (Minimum Viable Product — минимально жизнеспособный продукт)

**Суть принципа.** MVP предполагает реализацию минимального набора функций, достаточного для проверки идеи и достижения основной цели, без добавления необязательных возможностей.

**Применимость к проекту.** Принцип MVP полностью применим. В системе реализованы только ключевые функции:
- сбор новостей;
- оценка тональности;
- прогноз влияния на цену;
- сохранение результатов;
- визуализация в Grafana.

Отсутствуют такие элементы, как сложная пользовательская авторизация, гибкие роли, API для внешних клиентов и дополнительные интерфейсы управления. Это позволяет сосредоточиться на основной задаче — анализе новостного влияния — и не усложнять систему сверх необходимого.

### PoC (Proof of Concept — доказательство концепции)

**Суть принципа.** PoC направлен на проверку технической реализуемости идеи: работает ли выбранный подход, модели и архитектурные решения в принципе.

**Применимость к проекту.** Для данного проекта принцип PoC является уместным и частично реализованным. Реализация системы демонстрирует, что:

- новостные данные могут быть автоматически собраны;
- тональность текстов может быть рассчитана;
- результаты анализа могут быть связаны с ценовыми данными и визуализированы.

При этом система не претендует на промышленную точность прогнозов или высокую отказоустойчивость. Основная цель — подтвердить саму концепцию влияния новостей на рынок Bitcoin, что полностью соответствует идее PoC.
